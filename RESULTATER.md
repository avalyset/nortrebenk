## Limits

Limits stated in the analysis output (field `grenser`, in Norwegian): five repositories give five clusters, and clustered standard errors with so few clusters are uncertain (Miller §2.2 assumes independent clusters). The numbers are descriptive (NTB-0008), and there are no hypothesis tests.

Limits from the preregistration that still apply:

- v1.0 is not a ranking of agents, not a picture of the agencies' code, not a measure of licence value, not a measurement of a human with an agent and not a measurement of GitHub Copilot (NTB-0001). It measures one vendor (NTB-0012).
- The quality-check anchor consists of English-language Python tasks the models may have seen in training, including the outcome of the annotation. The set is Kotlin, TypeScript and C# with Norwegian and English text (NTB-0004). The Google rater was a free-tier model (AVVIK.md no. 4).
- The agent setup is not anchored to published solve rates (NTB-0007).
- The extended text was added after the outcome of P2.3 and the smoke test were known, and before any agent run on set tasks. The additions were written by a model from the same vendor as the agents, without human review; a task's pass may rest on the rater from the same vendor; and the additions state names and strings from the solution (NTB-0013).
- Claude Code can exceed the per-run budget cap: in the rehearsal, a cap of 0.02 USD gave a cost of 0.0441 USD (source: `data/roykprove/generalprove.jsonl`).
- Cost that Claude Code has not reported is not counted as spent. That covers a run interrupted when the runner stops, and an attempt discarded because the runner itself failed. B leaves 5.00 USD of the balance unused (NTB-0014).
- For the two kafka-manager tasks with build fields, the dependency caches come from the gold-patch state and show which dependencies the solution uses (`harness/agent/gullcache.py`).
- Sample: 21 tasks from 5 repositories in two GitHub organisations, navikt and Altinn, merged between 2026-11-02T12:58:35Z and 2026-11-14T23:10:08Z (source: `data/sett_v1.jsonl`).
- Validation was done with an own runner on linux/arm64, not through unmodified Multi-SWE-bench (AVVIK.md no. 1). The runner anchor against Multi-SWE-bench fell away (AVVIK.md no. 5).

Limits that follow from the numbers:

a. The main measure is at the ceiling for both arms: claude-sonnet-5-5 solved 61 of 61 runs (solved share 1.0000) and claude-opus-5-5 solved 59 of 61 (solved share 0.9524) (table T4). The pilot does not separate the two models.

b. The extended text was written with knowledge of the solution and states names and strings from it (NTB-0013). The solved share on the extended text is probably higher than it would be for a specification written without that knowledge, and the pilot does not measure by how much.

c. The PR text alone did not pass the quality check for 17 of 21 tasks (`utfall_p23` utelukket in `data/sett_v1.jsonl`), so the numbers for the PR text mostly describe underspecified tasks. On those tasks the solved share on the PR text was 0.0294 for claude-sonnet-5-5 and 0.0882 for claude-opus-5-5 (table T7).

d. The interval formula (Miller, equations 3 and 4) gives zero width when all task scores are equal (claude-sonnet-5-5 on the extended text: 1.0000 with interval [1.0000, 1.0000]). It also gives bounds outside 0–1 (claude-opus-5-5 on the extended text: per-task interval [0.8590, 1.0457]; claude-sonnet-5-5 on the PR text: clustered interval [-0.0147, 0.4433]). The intervals are reported as registered.

e. The supplement showed that single runs vary. For navikt/pensjonssimulator#688, claude-opus-5-5 solved 0 of 2 registered runs on the extended text and solved the supplementary run, while claude-sonnet-5-5 solved 2 of 2 registered runs and did not solve the supplementary run. For Altinn/altinn-access-management-frontend#2645, both arms solved their 2 registered runs and the supplementary run (tables T9 and T12).

f. The cross-check on amd64 was not run (AVVIK.md no. 12). The outcomes of the gold patch and the empty patch are shown on linux/arm64 only.

g. No run ended with an error, hit a cap or was discarded (table T3), so those paths of the runner have not been exercised on the set.

## Reproduction

```
python3 analysis/analyse.py data/p3/p3_kjoringer.jsonl --pass data/p3/p3_pass.jsonl --ut results/p3_registrert.json
python3 - <<'EOF'
import json
rader = [l for l in open("data/p3/p3_kjoringer.jsonl", encoding="utf-8") if l.strip() and json.loads(l)["status"] != "manglende"]
rader += [l for l in open("data/p3/p3_tillegg.jsonl", encoding="utf-8") if l.strip()]
open("results/p3_med_tillegg_inndata.jsonl", "w", encoding="utf-8").write("".join(rader))
EOF
python3 analysis/analyse.py results/p3_med_tillegg_inndata.jsonl --pass data/p3/p3_pass.jsonl --ut results/p3_med_tillegg.json
python3 analysis/lag_resultater.py --B 66.71
```

The tables use the stored rate in `results/valutakurs.json`. `python3 analysis/lag_resultater.py --hent-kurs` fetches the rate again and overwrites that file with a new retrieval time. B comes from the author's internal run log and is used only in table T2.
